# M0c 性能原型与快照耗时实测

目的:验证设计文档 v0.3 的 B10 门槛(每个场景 p95 ≤ 30ms),并实测 B3 快照算法在 1k / 10k 文件仓库上的耗时。
本文只记录有证据的结论;未实测的内容单独标为"未验证"。

## 结论摘要

| 问题 | 结论 | 证据 |
|---|---|---|
| Go 最小完整 hook(不含 git 快照)是否满足 p95 ≤ 30ms | **满足**。12 个场景、3 轮重复(场景 1–5、5b、7–11、X1),最差 p95 为 17.13ms(4 进程并发争锁,负载 16–20 的第 1 轮);其余场景最差 p95 ≤ 15.99ms | 下文表 1 |
| B3 快照算法(v0.3 字面版,调用 git 子进程)是否满足 30ms | **不满足**。普通 commit 的 C:p95 78ms(1k)/ 119ms(10k);`add -u` 的 S:p95 153ms(1k)/ 128ms(10k) | 下文表 2 |
| `git commit` 检查(B10 场景 6)端到端 | 字面版 **不满足**:p95 79.7ms(1k)/ 119.6ms(10k);`commit -a` p95 92.3 / 157.4ms | 表 1 的 6a–6d |
| 实验:C 快照改为进程内解析索引计算 tree id | 端到端 p95 **10.8ms(1k)/ 11.6ms(10k)**;tree id 与 `git write-tree` 在两个测试仓库上逐位一致 | 表 1 的 6e/6f、表 2 末行 |
| Stop 时的工作区快照 S(含 `add -u`) | **不满足**:端到端 p95 157ms(1k、10k 均是),本原型没有可行的缓解实现 | 表 1 的 8b/8c |

按 B10 与 M0 的约定:**存在超过 30ms 的场景(场景 6、以及 Stop 上的 S 快照),此处停下汇报,不放宽门槛**。
Go 语言选择在"hook 本体"层面成立;需要决策的是 git 快照的实现方式(见"建议与待决策")。

## 方法

**hook 原型**(`proto/m0c/hook/`,package main,每次进程执行完整流程):
读 stdin JSON → 加载 12 条规则(`proto/m0c/rules/rules12.json`;JSON 解析 + 校验,编译结果以规则文件 stat(路径、size、mtime_ns、inode)为键缓存为 gob)→ Bash 命令用 `mvdan.cc/sh/v3/syntax`(bash 方言)解析为命令节点(包装器剥离、`sh -c` 递归 ≤2 层、重定向写入、管道、async)→ 求值(三值逻辑,unknown 不命中)→ 状态文件 `flock`(非阻塞重试,上限 20ms)下读改写 + 临时文件 `rename` → 审计 JSONL 单次 `write`(`O_APPEND`)→ stdout 一次性输出 JSON。出错时 stdout 为空、stderr 带 `ballast:`、exit 1;150ms 看门狗。

12 条规则覆盖 PreToolUse(read-before-edit、no-long-sleep、evidence-before-commit、no-skip-verify、no-tamper-bash/edit、no-curl-pipe-sh、no-force-push、no-todo-stub)、UserPromptSubmit、Stop、PostToolUse 各一条。Bash 解析按计划 B1 回归集核对过(`go test ./proto/m0c/hook`,20 例通过)。

**bench**(`proto/m0c/bench/`):由外部父进程 `exec.Command(...).Run()` 起 hook 二进制,计时覆盖从启动到退出;每场景预热 20 次、正式 300 次;p95 取最近秩 `ceil(0.95n)`。每个场景使用独立的 `BALLAST_HOME`,`HOME` 指向 `.m0tmp`,git 配置隔离,不触碰 `~/.claude`、`~/.ballast`。每次运行都校验 exit code 和输出(如 Edit 场景必须输出 `deny`),"异常"列为校验失败数。对照组 `/usr/bin/true` 和 Go 空程序走同一套 spawn 路径。

场景说明:
- 场景 1 每次用新的 session_id(含建目录);2–4、7、8 复用同一 session,`tool_use_id` 每次不同,状态文件稳定在 `seen` 上限 512 附近(约 7–12KB)。
- 场景 5:100KB 命令 = 约 2500 条 `printf ... >> /tmp/x.log;` 语句(解析器最坏情形);5b 为补充的 100KB heredoc。
- 场景 9:每次迭代前删除缓存目录。场景 10:每轮 4 个进程同时启动、争同一 session/agent 的状态文件,300 轮 = 1200 个样本;结束后核对"状态写入成功次数 == 状态文件 n_events"。场景 11:每次运行前把状态文件改写成截断的 JSON。
- 场景 6(`git commit` 检查):hook 内真的调用快照(C = 复制索引→rm exempt→write-tree;`-a` 时为 S),与 evidence 记录比较。6a/6b 为普通 commit,6c/6d 为 `commit -am`。
- X1:状态写入加 `fsync`(darwin 上为 `F_FULLFSYNC`)。8b/8c:Stop 的 `claim-needs-evidence` 在有完成声明时触发 `verify_fresh`,计算工作区快照 S。

**快照测试仓库**(`scripts/m0c-bench.sh` 生成于 `.m0tmp/repos/`):1000 与 10000 个已跟踪文件,约 80% `.go`、10% `.md`、10% `docs/**/*.txt`,分布在 100 个顶层目录;提交后等 2 秒越过 racy-git 窗口并 `update-index --refresh`,再对 5 个已跟踪文件做未暂存改动(3 个 `.go`、1 个 `.md`、1 个 docs 文件)。索引大小 118KB(1k)/ 918KB(10k)。exempt 为 `docs/**` 与 `**/*.md`,与计划示例一致。
算法按 v0.3:`cp` 索引到临时文件 → 在 `GIT_INDEX_FILE` 下 `git add -u`(S 才有)→ `git rm --cached -r -q --ignore-unmatch -- ':(glob)docs/**' ':(glob)**/*.md'` → `git write-tree`。每个变体预热 3 次、正式 30 次,报告 p50/p95/max(n=30 时 p95 即第 29 小的样本,基本等于次大值)。bench 确认真实索引文件的哈希在测量前后不变。

## 瓶颈分析

**1. hook 本体:耗时主要是进程创建与 Go 运行时启动,不是业务逻辑。**
- 安静度较好的第 2、3 轮 p50:`/usr/bin/true` 2.0ms,Go 空程序 3.2–3.6ms,hook(场景 4)4.5–5.4ms。Go 运行时相对 `true` 多约 1.2–1.6ms;完整 hook 相对空程序再多约 1.3–2ms。
- hook 进程内部(审计里的分阶段耗时,p50):读 stdin 0.04ms、加载规则(gob 缓存命中)0.09ms、读状态 0.06ms、求值 0.02ms、状态事务(flock + 写临时文件 + rename)约 0.3ms,整体 0.5ms 左右。这不包含 exec 与运行时初始化。
- 最重的 hook 内工作是 100KB 语句序列的 mvdan 解析:p50 1.44ms(进程内总计 2.77ms);heredoc 形式只有 0.43ms。
- 12 条规则冷缓存:加载规则从 0.09ms 升到 0.42ms,整进程 p95 与热缓存差异落在噪声内(8.3–13.5ms 对 7.4–12.1ms)。**在 12 条规则的规模下,gob 缓存只省约 0.3ms**。`*regexp.Regexp` 不能 gob 序列化(只能存源码文本),所以本原型缓存的是校验后的规则结构,正则在求值时按需惰性编译。
- 状态写入若加 `fsync`(darwin 为 `F_FULLFSYNC`),状态事务从约 0.3ms 升到约 4.3ms,整进程 p50 增加约 3.4–4.4ms(X1 对场景 4,第 2、3 轮);仍在门槛内,但这是需要明确决定的项,本原型默认不 fsync。
- 并发争锁:4 进程同时起,p95 8.2–17.1ms,未触发 20ms 锁超时。

**2. git 快照:瓶颈是子进程数量与 `git rm --cached` 的 pathspec 步骤。**
- 在当前负载下,启动一个空转的 git 进程就要 p50 约 9.6ms,因此字面版的 3–4 个 git 进程(rev-parse、add -u、rm、write-tree)仅启动开销就接近或超过 30ms。
- `git rm --cached ... ':(glob)...'` 是单步最慢的:1k 约 29–34ms,10k 约 58–64ms,**随文件数近似线性增长**(1k→10k 约 2 倍,而 `write-tree` 只从约 12ms 到约 17ms)。这一步不只是进程启动成本。其内部原因本原型没有做进一步剖析,不下结论。
- `add -u` 在 1k/10k 约 17 / 23–25ms;`cp` 索引在 10k 约 3ms(进程内复制约 0.5ms);直接定位 `.git/index` 可省掉约 10ms 的 `rev-parse`。
- 因此即使去掉 `rev-parse` 和外部 `cp`(优化版),C 仍有 41ms(1k)/ 78ms(10k) 的 p50,超过门槛。
- 实验:C 不需要读工作区,可以直接解析索引(v2/v3)→ 按 exempt 过滤 → 在内存里构造 tree 并算 SHA-1。实现在 `proto/m0c/nativetree/`(约 160 行)。耗时 0.28ms(1k)/ 2.2ms(10k),hook 端到端 p95 约 11ms。它对 v4 索引、扩展标志(skip-worktree / intent-to-add)、未合并条目、sparse 目录、split index 会返回 `ErrFallback` 退回 git。
- 该实验**只证明 C(不含 `add -u`)可以不启动 git 子进程**。S 需要读工作区(`add -u` 的语义含 clean/smudge 过滤器、`core.filemode`、符号链接、删除文件等),本原型没有实现原生版,S 仍是 78–157ms。

## 建议与待决策

以下为基于上述数据的建议,其中"未验证"的部分没有实测。

1. **B3 的 C 快照不要调用 git 子进程。** 原生解析索引已在本机验证可行;需要决定:是否接受"原生实现 + 不支持情形退回 git"的双路径,以及退回路径是否仍计入 30ms 门槛(退回时必然超标)。
2. **B10 场景 6 的 30ms 门槛对 S / `commit -a` / Stop 无法用 git 子进程达成。** 可选方向(均未验证):(a) 把需要工作区快照的检查移出 hook 热路径,只在 `ballast verify` 的 runner 中算 S;(b) 对 `commit -a` 与 Stop 的 `verify_fresh`,在 hook 里只做廉价判断(例如与 evidence 记录的索引指纹比较),取不到确定答案时返回 unknown(fail-open);(c) 对 S 放宽门槛并明文写入计划。这是需要主控或用户决策的点,本原型不替代决策。
3. 计划 Risk 4 提到的"以索引 stat 为键做缓存"没有实现;原生 C 方案已使 C 路径不需要缓存。
4. 规则缓存(gob)在 12 条规则下收益约 0.3ms,可以在 M1 评估是否值得保留;热更新所需的 stat 检测仍然需要。
5. 状态事务是否 `fsync` 需要决定(约 +4ms,仍在门槛内)。
6. hook 内的状态事务采用"无锁读取用于求值,加锁后重读并合并增量再写",以缩短持锁时间;并发场景未出现丢失更新。若 M1 采用"整个求值都在锁内",持锁时间会随求值(含快照)拉长,争锁超时概率上升——这一点未实测。

## 审计补注(Opus 审计,结论 accept)

- 表 1 的 6a–6d、8b/8c 使用的是 git 子进程**优化版**(直接定位 `.git/index` 并在进程内复制),不是字面版。优化版仍然超标,字面版只会更慢。
- p95 ≥ 150ms 的场景受看门狗截断,属于删失值。审计员在负载约 10 时重跑:8b 的 p95 为 62.7ms,6a/6b 为 53.2/74.7ms,原生 C(6e/6f)为 5.5/7.8ms,核心场景为 4.9–8.1ms。结论不变。
- 原型在 `main` 中执行了 `debug.SetGCPercent(-1)`(关闭 GC)。M1 需要沿用该设置或重新测量。
- 看门狗的 `os.Exit` 不会杀掉 git 子进程,也不会执行 defer,导致临时索引残留在 `.git/` 下。M2 必须做到三点:用 `exec.CommandContext` 加进程组 kill;临时索引放在 `BALLAST_HOME` 或系统临时目录;fault 测试断言 `.git` 下没有残留。
- bench 的门槛判定必须同时满足 `Bad==0`、样本数齐全和 `p95≤30`。spawn 全部失败时不能报告为通过。
- 多客户端调用路径(Codex 的 apply_patch、Cursor 的 beforeShellExecution 等)的开销本次未测,由 M1 bench 为每个 `--client` 增加场景。

## 局限与未做的事

- 机器全程繁忙(load 12–20),没有空闲基线;没有 `hyperfine` 交叉校验;只有 macOS arm64。
- 每个场景只在 1 台机器上跑 1–3 轮;场景 6、8b/8c 与快照表只有 1 轮,快照表 n=30。
- 原型只实现 12 条规则的最小 DSL 子集,不代表完整 DSL 的求值成本;PowerShell 分词器未实现。
- 原生 tree 与 git 的一致性只在 2 个测试仓库、`docs/**` + `**/*.md` 两条 exempt 上核对;doublestar 与 git `:(glob)` 在更复杂 pattern 上的语义差异未系统验证。
- 未实现 B7 的故障注入测试与热更新验收;看门狗仅通过"git 场景超时 → exit 1"间接观察到。
- 本任务不涉及安装 / 卸载(B12 / M4)与不同 AI IDE 的适配:原型不读写任何 settings 文件,运行状态只在 `BALLAST_HOME` 指向的临时目录。
